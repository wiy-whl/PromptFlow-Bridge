01
PROBLEM · 问题层

先讲清楚：用户在哪、卡在哪

背

行业背景

大理是高频自由行目的地，但信息极度分散——景点攻略在一处、非遗体验在另一处、交通与排程又靠游客自己算。游客在做行前规划时往往要在 3 个以上工具间反复横跳。

题

设计命题

如何把“洱海、喜洲、双廊、苍山、三塔”这些散点，和“扎染、制茶、白族菜”这些非遗，统一成一条用户真的能走完的行程？——让规划从“负担”变成“被安排好的安心”。

三个真实痛点
01

信息分散，决策累

景点、非遗、交通各在不同平台，游客做规划要在多个 App 间反复横跳，行前焦虑重。

痛点跨 3+ 工具拼凑攻略，决策成本高。
02

文化只看不体验

白族扎染、制茶、白族菜多为“介绍页”，缺少可加入行程的体验入口，文化停在浏览层。

痛点非遗内容无行动出口，转化率极低。
03

行程靠手排，算不清

景点间路途、开放时间、天数限制都要人肉估算，新手极易排崩或漏掉关键动线。

痛点路途/时间靠脑算，行程可行性差。
目标 & 用户

目标一 · 一站收敛

景点 + 非遗 + 交通在一个产品内闭环，减少跨工具切换。

目标二 · 文化可执行

每个非遗都能“加入行程”，从内容变成可预约的体验。

目标三 · 排程可计算

选好景点与天数，系统给出可行的时间轴与交通建议。

用户画像 · 自由行新手

首次到大理、信息焦虑、希望被“安排好”，愿意为省心买单。

用户画像 · 文化体验者

冲着非遗与在地生活而来，要的是“能参与”而非“能围观”。

SOLUTION · 方案层

两句话讲清策略，再放关键页面

把分散的大理“收口”成一个产品：
内容给逛法，文化给出口，行程给算法。
A

内容 · 有逛法

每个景点不再只是图集，而是“可以这样逛 / 现场 / 接下来去”，把信息变成动线。

B

文化 · 可执行

非遗从介绍页升级为可加入行程的体验单元，一键进入规划，文化真正落地。

C

行程 · 可计算

规则引擎按距离/天数/开放时间自动排程，给出逐小时时间轴与交通建议。

关键决策 · 每个都标注“这里解决了什么”
决策 01 · 内容有“逛法”

景点详情页：从图集到动线

传统详情页是图片+文字堆砌。我们给每个景点三段式结构——“可以这样逛 / 现场 / 接下来去”，把浏览转成行动。

痛点信息分散、不知怎么玩。
做法三段式动线 + 顺路推荐。
解决一页内完成“看→决定→接续”。
决策 02 · 文化有“出口”

非遗文化页：从围观到加入

扎染、制茶、白族菜不再是静态介绍，每个体验都有「加入行程」入口，文化单元直接汇入规划器。

痛点文化只看不体验。
做法体验单元 + 一键加入行程。
解决非遗成为行程的一部分。
决策 03+04 · 行程可计算（核心）

规则引擎：选景点→自动排一天

用户在清单勾选景点与天数，引擎按就近原则排序、判定交通方式（步行/包车），生成逐小时时间轴；排不下的会诚实提示“这几天排不下”。

痛点路途/时间靠脑算，易排崩。
做法距离+天数+开放时间规则排程。
解决一键得到可行行程，含交通建议。
决策 05 · 状态完整性

把“出错”也设计进去

加载、空状态、失败——三类非理想路径都给出明确引导，而不是白屏或死等，保证全流程可用。

痛点异常态无引导，体验断裂。
做法统一空/加载/失败三态文案与出口。
解决任何状态用户都知道“下一步”。

设计预期（待验证）

· 跨工具切换次数：预期从 3+ 降到 1 内
· 非遗体验转化：从“仅浏览”到有明确行动入口
· 行程可行性：规则排程替代人工脑算，降低排崩率

下一步验证计划

· 招募 5 名自由行用户做可用性测试
· 埋点：加入行程率 / 排程完成率 / 跳出点
· 与业务方对齐“自动排程”命名与能力边界

设计反思 · 诚实比好看更重要

原型里「AI 推荐行程」按钮命名超出了当前规则引擎的实际能力——它本质是确定性排程而非模型推理。我已在复盘里建议改名为「自动排一天」，避免对业务方与用户产生能力预期偏差。

另一个反思：状态完整性常被忽略。我专门补齐了加载 / 空 / 失败三态，因为“出错也被设计过”才是完整产品。
